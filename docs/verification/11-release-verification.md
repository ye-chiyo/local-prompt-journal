## Windows 开销测量

Python 3.12.8；5 对启用／停用采集器的独立进程，交替条件次序，每次 24 个受控生产更新，共各 120 个更新。相同 SHA-256 工作量和原子 JSON 写入，目标更新间隔 200ms，启用条件采集间隔 100ms、分页大小 100、3 会话／2 项目；无附件 I/O、无模型调用。实际每次持续约 4.8 秒；发生较慢保存时节拍按实际耗时延长，不把目标节拍当作精确时间保证。用 `GetProcessTimes`、`GetProcessMemoryInfo`、`GetProcessIoCounters` 取得父进程及外部受控来源进程计数。

启用条件还专门运行观察者，每 5ms 调用一次公开 `Journal.session()` 检查保存是否跟上；其 SQLite 查询、反序列化和历史关系视图成本也计入父进程 CPU。停用条件没有等价观察者。所以下表 CPU 是“生成器＋采集＋受控来源＋公开视图轮询”的混合计数，CPU 工作负载并不对称，启停差量不能归因于纯采集器。原始量值和旧报告保持不变；工具当前的 `scope` 已明确此限制，严格性能验收继续为部分完成。

建议后续在默认 3 秒周期、稳定且更大样本上另行确认预算：来源发布后 P95 保存延迟不超过 5 秒，隔离观察者后采集器加来源进程的长期 CPU 低于单核 10%，合计工作集低于 150MiB；同时记录 100 次更新及长会话下的目录增长再确定保留策略。这些是待确认建议，不是既定验收阈值；当前混合 CPU 读数不能证明建议达标，不把它标为性能通过。

原性能脚本使用相对受控来源目录；所有启停条件在同一 worktree／cwd，比较条件未因其而改变。最终演示样本改为绝对来源身份只修正跨工作区复用，不影响已记录性能算法或计数；不覆盖旧报告。仓库测量工具还对 Windows 计数失败明确报错，避免未来将失败的零值记作有效读数。
